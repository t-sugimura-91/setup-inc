WordPressが遅い。サーバーを変える前に確認する3つのこと

サイトの表示が遅いと、「サーバーを変えれば直るのでは」と考えがちです。ただ、遅さの原因はサーバーとは限りません。変える前に確認しておきたいことを、Googleの公式情報をもとに整理しました。

WordPressのサイトを運営していると、「最近、表示が遅い」と感じる場面があります。広告を出しているサイトなら、なおさら気になるはずです。クリックして来てくれた人がページの表示を待たずに戻ってしまえば、広告費が無駄になります。

そこで「サーバーを乗り換えよう」と考える人は多いのですが、移転にはデータの移行、DNSの切り替え、計測の確認といった手間がかかります。しかも原因が別のところにあれば、移転しても遅いままです。この記事では、乗り換えを決める前の確認事項を3つに分けて説明します。

結論:先に「どこが遅いのか」を切り分ける

  • まず、Googleが公式に示している指標で計測します。感覚ではなく、数字で遅さを確認します。
  • 計測の結果、サーバーの応答時間(TTFB)が目安を大きく超えているなら、サーバー変更を検討する価値があります。そうでなければ、画像やプラグインなど別の原因を先に疑います。
  • 変えると決めた場合は、広告のリンク先と計測タグを壊さない手順で進めます。

以下、順に説明します。

確認1:まず、Googleの指標で計測する

表示速度は、体感だけで判断しないほうが確実です。Googleは検索セントラルで、ページの使いやすさを測る「Core Web Vitals」という3つの指標を案内しています。

指標何を測るかGoogleが示す目安
LCP読み込みパフォーマンスページの読み込み開始から2.5秒以内
INP応答性200ミリ秒未満
CLS視覚的な安定性0.1未満
 出典:Google 検索セントラル「Core Web Vitals と Google 検索の検索結果について」(2026年11月19日確認)

同じページで、Googleは、Core Web Vitalsを「Googleのコアランキングシステムがランキングを決定する際に考慮する要素」の1つと説明しています。つまり、表示速度は読者のためだけでなく、検索からの集客にも関わります。

測る方法は2つです。

  • PageSpeed Insights:URLを入れると、そのページの数値と改善の候補が出ます。
  • Search Consoleの「Core Web Vitals」レポート:サイト全体で、改善が必要なページがどれかを確認できます。

まず、広告のリンク先に使っているページと、アクセスの多いページを測ります。数値が目安の範囲に入っているなら、サーバーを変える必要性は低いと判断できます。

PageSpeed Insightsの数字の読み方

PageSpeed Insights(PSI)の画面には、数字が何種類も並びます。見る順番と、読み方の注意点を、Googleの公式ドキュメントにもとづいて整理します。

「フィールドデータ」と「ラボデータ」は別物

PSIは、同じページについて2種類のデータを見せます。

  • フィールドデータ:実際のユーザーの体験です。Chromeユーザーエクスペリエンスレポート(CrUX)にもとづき、過去28日間の値が表示されます。実態を把握するのに向いていますが、使える指標は限られます。
  • ラボデータ:制御された環境でページの読み込みをシミュレートした値です。問題のデバッグに役立ちますが、実際のボトルネックを捉えていない場合がある、とGoogleは説明しています。

公式のFAQには、この2つの値が食い違うことがあると書かれています。実際のユーザーの体験を知りたいときはフィールドデータ、原因を探るときはラボデータ、と使い分けます。

なお、アクセスの少ないページや公開したばかりのページは、フィールドデータが表示されないことがあります。その場合、PSIはサイト全体の値に切り替えます。それも不足している場合は、フィールドデータは表示されません。

評価のしきい値

PSIは、実際のユーザーの体験を「良好」「改善が必要」「低い」の3段階で評価します。値は、全ユーザーのうち75パーセンタイル(最も不満を感じやすい側の値)で見ます。

指標良好改善が必要低い
LCP2,500ミリ秒以下〜4,000ミリ秒4,000ミリ秒超
INP200ミリ秒以下〜500ミリ秒500ミリ秒超
CLS0.1以下〜0.250.25超
FCP1,800ミリ秒以下〜3,000ミリ秒3,000ミリ秒超
TTFB(試験運用版)800ミリ秒以下〜1,800ミリ秒1,800ミリ秒超
 出典:Google for Developers「PageSpeed Insights について」(2026年11月19日確認)。TTFBは「試験運用版」と表記されています。

Core Web Vitalsの3指標(LCP、INP、CLS)は、すべての75パーセンタイルが「良好」であれば、評価に合格します。

ラボのスコア(0〜100)の見方

画面の上部に出る大きなスコアは、ラボデータにもとづく点数です。90以上が「良好」、50〜89が「改善が必要」、50未満が「不良」とされています。ただし、公式ドキュメントでは、ラボデータが良好でも、実際のユーザーの体験が良いとは限らないと注意されています。点数を上げること自体を目的にせず、フィールドデータと合わせて見るのが基本です。

測定条件を知っておく

  • ラボデータは、ミッドティアの端末(Moto G4)で、モバイルならモバイルネットワーク、デスクトップなら有線接続を想定して計測されます。
  • テストは、Googleのデータセンターで実行され、場所は北米・ヨーロッパ・アジアのいずれかです。そのため、サーバーが国内にあっても、計測の場所によってTTFBの値は変わりえます。1回の計測で判断せず、時間を変えて数回測ります。
  • 公式のFAQには、パフォーマンススコアが実行のたびに変わる理由の項目もあります。数点の違いに一喜一憂しないほうがよい、ということです。

確認2:サーバーが原因かどうかを見分ける

数値が悪かったとき、次に見るのは「遅さの種類」です。サーバーが関係するのは、主に最初のバイトまでの時間(TTFB)です。

TTFBは、ページを要求してから、サーバーの返事の最初のデータが届くまでの時間です。Googleのweb.devでは、ウェブサーバーが要求にどれだけ速く応えられるかを見る基本的な指標と説明されていて、目安は次のとおりです。

  • 0.8秒以下:良好
  • 1.8秒超:不適切

ここで2つ、注意点があります。

  1. TTFBはCore Web Vitalsの指標ではありません。web.devもその旨を明記しています。TTFBが良くても、LCPが悪ければ「遅い」ページです。逆に、TTFBは目安を少し超えていても、ほかの指標が良ければ大きな問題にならない場合もあります。
  2. TTFBが悪い原因は、サーバーの性能だけではありません。web.devでは、TTFBを「リダイレクト、DNSの検索、接続とTLSのやり取り、要求から返事までの時間」の合計と説明しています。リダイレクトが多いだけでも、TTFBは伸びます。
計測で見えた状況疑う場所サーバー変更が効きそうか
TTFBが1.8秒を超えるサーバーの応答、重い処理、リダイレクトの多さ可能性あり(まずリダイレクトと処理の重さを確認)
TTFBは良好、LCPが悪い大きな画像、読み込みが遅い要素低い(画像などの対策が先)
INPが悪いブラウザ側の処理(スクリプトなど)低い
CLSが悪い画像・広告枠のサイズ指定、あとから挿入される要素ほぼなし
 指標の意味は、上記のGoogle公式の説明にもとづく整理です。原因の切り分けは目安で、実際には複数が重なることもあります。
「サーバーを変えたのに変わらない」は珍しくない LCPやINP、CLSの悪化は、サーバーの外側にある原因で起きることがあります。計測の結果が「TTFBは良好」なら、サーバーを変えても数値はほとんど動かない可能性が高いと考えられます。

確認3:サーバーを変える前にできる対策

サーバー変更は手間も費用もかかるので、先にできる対策を試すほうが負担は軽く済みます。エックスサーバーの公式ブログ「WordPressブログが重い原因と対策」では、すぐにできる対策として次のようなものが挙げられています。

  • 画像を圧縮する
  • 動画は、YouTubeにアップしたものを埋め込む
  • プラグインを整理する
  • ウィジェットのコンテンツを整理する
  • 不要なファイルを削除する
  • WordPressやプラグインをアップデートする

同じ記事では、重くなる原因として「画像や動画の読み込みに時間がかかっている」「不要なデータが溜まっている」「サーバーの性能が合っていない」の3つが挙げられています。サーバーの性能は、原因の1つにすぎないという位置づけです。

こうした対策をしたうえで、もう一度PageSpeed Insightsで測ります。それでもTTFBが目安を超える状態が続くなら、サーバー変更を検討する材料がそろったことになります。

移転の進め方:自分でやる場合と代行を頼む場合

移転する場合、方法は大きく2つです。ここでは、エックスサーバーの公式マニュアルと公式ページで確認できる内容を整理します。

自分で移行する(エックスサーバー「WordPress簡単移行」)

他社サーバーで動いているWordPressを、必要な情報を入力するだけでエックスサーバーへ移す機能です。公式マニュアルの流れは次のとおりです。

  1. 移行先のドメイン設定を、あらかじめ済ませておく
  2. サーバーパネルで「WordPress簡単移行」→「WordPressを移行」を選ぶ
  3. 移行元のURL、WordPressのユーザー名とパスワード、移行先のURLを入力して実行する(実行中のキャンセルはできません)
  4. 処理が終わったら、「確認しました」を押す
  5. ネームサーバーを変更し、サイトの動作を確認する

使う前に、公式マニュアルの「ご利用上の注意」で、次の点を確認します。

  • 動作要件:WordPressのバージョンが4.2〜7.1、PHPが7.2以上であること。
  • エラーになるケース:マルチサイト機能を使っている、データベースが2GBを超える、WordPress.comからの移行、など。
  • 移行されるデータ:/wp-contentフォルダのデータ(画像、プラグイン、テーマ)と、データベースの内容(記事や各種設定)。
  • 移行されないデータ:移転元の「.htaccess」、バックアップ系プラグインが作ったデータ、/wp-content以外のデータやプラグイン設定。キャッシュ関連・セキュリティ関連のプラグインは該当する可能性があると案内されています。
  • ネームサーバーの変更は、移行の完了後に行うこと。

特に注意したいのは、「.htaccess」が移行されない点です。リダイレクトの設定などを.htaccessに書いている場合は、移行後に設定し直す必要があります。広告のリンク先がリダイレクトに依存している場合は、移行直後に確認してください。

移転で広告と計測を壊さないための確認

広告を出しているサイトでは、サーバーの移転作業そのもの以上に、移転中に広告のリンク先が表示されなくなることが大きなリスクになります。広告費は、表示されないページにも発生します。移転の前後で、次の点を確認します。

  1. 広告のリンク先URLが変わらないか。ドメインが同じで、パスも変わらないなら、広告側の変更は不要です。URLが変わる場合は、広告のリンク先をすべて差し替えます。
  2. DNSの切り替えのタイミング。切り替えの間は、古いサーバーと新しいサーバーの両方にサイトを置いておき、新しいサーバーで表示を確認してから切り替えます。アクセスの少ない時間帯に行うと、影響を小さくできます。
  3. 計測タグ(Googleタグマネージャー、GA4など)が、移転後も動いているか。コンバージョンの計測が止まると、広告の成果を判断できなくなります。移転の直後に、テストのコンバージョンで確認します。
  4. SSL(https)が有効か。両社とも無料の独自SSLを案内しています。移転後にhttpでの表示になっていないかを確認します。
  5. リダイレクトの設定が引き継がれているか。古い設定が抜けると、リダイレクトの連鎖や表示エラーの原因になります。TTFBの悪化にもつながります。
  6. 移転の前後で、同じページの数値を比べる。確認1で計測した数値を、移転後にもう一度測り、改善したかを確かめます。

WordPressの移行を自動で行う機能(エックスサーバーの「WordPress簡単移行」)や、移転を代行するオプションもあります。不安がある場合は、こうしたサービスを使うのも選択肢です。

よくある質問

Q. サーバーを変えれば、Core Web Vitalsは必ず良くなりますか?
いいえ。Core Web Vitalsの指標の中には、サーバーの外側の要因で決まるものがあります。web.devもTTFBはCore Web Vitalsの指標ではないと説明しています。先に、どの指標が悪いのかを計測で確認してください。
Q. 表示速度は、検索順位に関係しますか?
Googleは、Core Web Vitalsを、コアランキングシステムが考慮する要素の1つと説明しています。ただし、順位は多くの要素で決まるため、速度だけで順位が決まるわけではありません。AI検索への対策について、Googleが公式に説明している内容は、「AIO診断を受ける前に知っておきたいこと」で整理しています。
Q. 無料のお試しがあれば、先に試したほうがいいですか?
エックスサーバーは最大10日間の無料お試しを案内しています。お試しの環境で、自分のサイトを動かして表示を確認できるかを、先に確かめておくと安心です。
Q. 計測は、どのページから始めればいいですか?
広告のリンク先に使っているページ、アクセスの多いページ、コンバージョンに近いページの順がおすすめです。

まとめ

WordPressの表示が遅いとき、サーバー変更は有力な選択肢の1つですが、最初の一手ではありません。

  • まず、PageSpeed InsightsとSearch Consoleで、Core Web Vitalsを計測する
  • TTFBが目安(0.8秒以下)を大きく超えるときに、サーバー変更を検討する
  • 変える前に、画像・プラグイン・不要なファイルの対策を試す
  • 移転では、広告のリンク先と計測タグを壊さない手順で進める

広告の成果は、広告管理画面の中だけでは決まりません。クリックの先のページが速く表示され、正しく計測できることも、広告運用の土台です。

移転先を検討するなら、まず無料お試しで確認
